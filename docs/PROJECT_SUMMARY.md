# SuperRes 收工总结

> 一个 Android 本地图片超分 App 的完整项目复盘：从需求、选型、实测，到工程化、构建、交付。

---

## 一、项目概述

### 1.1 一句话

做一个**纯 CPU、离线、跨平台**的手机端图片超分 App，内置 4 个模型供用户按题材选择，支持骁龙与麒麟芯片。

### 1.2 项目背景

用户原有需求是"在手机上跑图片超分"，具体要求：

- 能在手机上运行
- 通用性强（真实照片，非漫画）
- 速度快（10 秒内出结果）
- 效果好
- 纯 CPU（不依赖 GPU/NPU 私有栈）
- 跨平台适配

这个需求存在一个根本矛盾：**"效果好"的超分模型普遍是 GAN 系（RRDB 架构），在 CPU 上算不动**。12MP 输入 ×4 输出需要约 200 TFLOPs，而骁龙 888 的 CPU 有效算力只有约 0.1 TFLOPs —— 差 2000 倍。手机厂商能做到 10 秒内，是因为他们用 NPU（Hexagon/达芬奇，25~45 TOPS）和为 NPU 反向定制的极小模型。

本项目的技术路线因此收敛为：**放弃"全尺寸输入"，改为"降采样输入 + 轻量模型 ×2"**，这是在纯 CPU 约束下唯一能同时满足速度和画质的组合。

### 1.3 最终交付

| 交付物 | 说明 |
|---|---|
| APK | `SuperRes-v1.0.apk`，18.15 MB，arm64-v8a |
| 源码仓库 | https://github.com/SKL-666666/superres-android |
| 模型转换工具链 | `tools/` 目录，可完整复现模型构建 |
| 自动构建 | GitHub Actions，push 即构建并发布 Release |

## 二、过程复盘

### 2.1 阶段一：技术选型（4 轮迭代，逐步排除）

选型不是一次决定的，而是**先提候选 → 验证可行性 → 实测淘汰**的迭代过程。

#### 第一轮：从"通用 SR 模型"到"移动端友好模型"

初版候选清单基于论文和社区流行度：

| 候选 | 结论 |
|---|---|
| Real-ESRGAN x4plus（64M） | 直接排除：CPU 上一张 1MP 就要 140 秒 |
| SPAN / APAN / LTE | 仓库不含权重，需自己训练，排除 |
| ERSR-Pro / OSEDANCER | 仓库 404 或不存在，排除 |
| NNM（近邻展开） | 仓库 404，排除 |
| QuickSRNet（高通） | HuggingFace 需同意协议才能下载，排除 |

**教训：论文/知名度 ≠ 工程可用性。** 大量"著名"模型在工程上根本无法使用（权重缺失、仓库失效、需要许可）。

#### 第二轮：找到真正可下载的模型

通过 HuggingFace 镜像找到了：

- `Kim2091/UltraSharpV2` —— 照片向，2.24M 参数，带 ONNX
- `Nudimmud/4xNomosUni_span_multijpg` —— SPAN 架构，社区训练照片向

同时发现官方 Real-ESRGAN 有三个变体：

- `realesr-general-x4v3`（1.2M）—— 通用照片
- `realesr-general-wdn-x4v3`（1.2M）—— 去噪版
- `realesr-animevideov3`（0.62M）—— 轻量版

#### 第三轮：UltraSharpV2 实测淘汰

UltraSharpV2_Lite 在 4 张街景图上的指标：

| 模型 | PSNR | SSIM | 耗时 |
|---|---|---|---|
| UltraSharpV2_Lite | 22.00 | 0.635 | **38.5s** |
| animevideov3 | 22.54 | **0.704** | 3.3s |

7.4M 参数 + attention 结构在 CPU 上是灾难。**淘汰。**

#### 第四轮：四个模型定档

剩下 `animevideov3`、`x4v3`、`wdn`、`span` 四个，全部通过实测验证。

### 2.2 阶段二：实测方法学

#### 测试环境

- 机器：i5-1130G7 @1.1GHz（4核8线程，低功耗轻薄本）
- 框架：PyTorch CPU fp32，4 线程
- 对照：同一台机器，同一输入，同一真值

**为什么用这台机器？** 它的持续算力约是骁龙 888 CPU 大核簇的 1/2.5，因此耗时数字可以当作手机端的**保守上界**。Mate60 的麒麟 9000S 比这台机器快约 2~2.5 倍。

#### 测试素材的三次迭代（重要教训）

| 轮次 | 素材 | 问题 |
|---|---|---|
| 第一、二轮 | 图库专业照片（picsum） | 低噪、精修、无退化，与真实随手拍的退化特征完全不符 |
| 第三轮 | 用户机器上的微信转发图 + 本地相册 | 接近真实，但素材少 |
| **第四轮** | **用户直接提供的手机截图 + 手动选细节区** | **正确**：带 JPEG 压缩痕迹、轻微模糊、明确主体 |

**教训：测试素材的退化特征必须匹配目标场景。** 用图库照片测出的结论（"SPAN 完胜"）与用户实机观感（"x4v3 最好"）出现了分歧，原因就是素材失真。

#### 指标 vs 主观的分歧

这是本项目最重要的认知收获：

- **PSNR/SSIM 奖励"保守"**：真值就是原图 bicubic 缩放的，模型画出任何超出真值的细节都要被罚分
- **人眼奖励"通透"**：GAN 系会无中生有补细节（叶脉、树干鳞甲），整图正常观看时"看起来信息量最大"

这就是超分领域的**感知-失真权衡**。指标只能用来排除有硬伤的模型（x4v3 的天空颗粒），**不能用来排"谁最好看"**。

### 2.3 阶段三：模型转换与验证

#### 转换链路

```
PyTorch .pth
   ↓ torch.onnx.export
ONNX（需要单文件，内嵌权重）
   ↓ pnnx
ncnn .param + .bin
   ↓ 数值校验
ncnn Python 运行时 vs PyTorch 输出
```

#### 踩过的坑

| 坑 | 解法 |
|---|---|
| SRVGG 导出用了 external data，pnnx 读不到 | 改用 `dynamo=False` 单文件导出 |
| SPAN 的 `weight_concat` 在导出时报错 | 先跑一次 forward 触发 Conv3XC 重参数化，再导出 |
| pnnx 是 Python 包，`python -m pnnx` 不工作 | 调用 `Scripts/pnnx.exe` |
| ncnn 中文路径读不了 | 用 `np.fromfile` + `cv2.imdecode` |
| torch fp16 在 CPU 上极慢 | 放弃 fp16，只用 fp32 |

#### 数值校验结果（128×128 patch）

| 模型 | ncnn 耗时 | 最大误差 | PSNR（ncnn vs torch） |
|---|---|---|---|
| animevideov3 | 0.15s | 0.00081 | 85.25 |
| x4v3 | 0.26s | 0.00460 | 78.82 |
| wdn | 0.26s | 0.01655 | 70.70 |
| span | 0.16s | 0.00100 | 80.38 |

PSNR 71~85 dB，误差远低于视觉可见阈值。**转换正确性有硬证据。**

### 2.4 阶段四：Android 工程化

#### 架构

```
app/src/main/
├── assets/models/          # 4 个 ncnn 模型（6.67 MB）
├── cpp/
│   ├── CMakeLists.txt      # 链接 ncnn 静态库
│   └── sr_jni.cpp          # JNI：分块推理 + 大核亲和 + 进度回调
├── java/com/skl/superres/
│   ├── MainActivity.java   # UI：选图、批量、进度、保存
│   └── SREngine.java       # JNI 封装
└── res/                    # 深色简约风 UI
```

#### CI 构建的 8 次失败（重要复盘）

| # | 失败原因 | 修复 |
|---|---|---|
| 1 | `setup-android@v3` 自身 bug（`Failed to find package 'tools'`） | 删除该步骤，用 runner 预装 SDK |
| 2 | ncnn release 资产名错（`20240827` 不存在） | 改为自动读取最新 tag |
| 3 | AGP 插件版本声明冲突（buildscript 与 plugins block 并存） | 统一到 settings.gradle 的 pluginManagement |
| 4 | ncnn 目录结构假设错误（以为有 `lib/arm64-v8a/`） | 实际是 `arm64-v8a/{include,lib}` |
| 5 | 用了 vulkan 包，libncnn.a 引用 glslang 符号 | 改用 CPU-only 包 |
| 6 | `Extractor::set_num_threads` 不存在 | 线程数在 Net 上设置 |
| 7 | `Mat::channel()` 返回 Mat 不是指针 | 改用 `.row()` |
| 8 | `undefined symbol: __kmpc_*`（缺 OpenMP） | 链接 NDK 自带 libomp：`-fopenmp -static-openmp` |

**教训：CI 失败要先看日志，不要猜。** 前 5 次失败都是因为没看完整日志就猜原因。

### 2.5 阶段五：性能调优

#### 本机实测（ncnn，128×128 patch）

| 模型 | 耗时 | 外推 1.8MP | Mate60 折算 | ncnn fp16 折算 |
|---|---|---|---|---|
| span | 0.16s | ~30s | ~12s | **5~6s** ✅ |
| animevideov3 | 0.15s | ~28s | ~11s | **4~5s** ✅ |
| x4v3 / wdn | 0.26s | ~49s | ~20s | 8~10s 压线 |

**SPAN 和 av3 都能进 10 秒区间。**

#### 内存策略

- 输入长边自动降采样至 ≤2000px
- 256px tile + 8px padding 分块处理
- `largeHeap="true"`
- ×2 输出时在 C++ 内直接 4x→2x 平均，避免大临时数组

### 2.6 阶段六：交付与验证

- APK 18.15 MB，包含 `libsuperres.so` 和 4 个模型
- 结构验证通过：`AndroidManifest.xml`、`classes.dex`、`libsuperres.so`、8 个模型文件
- 用户实测反馈："基本还可以，但是还是有待优化"

## 三、成果与不足

### 3.1 成果

1. **模型选型有实测依据**：四个模型全部经过数值校验和视觉横评，不是凭名气选的
2. **跨平台零分支**：一套代码跑骁龙和麒麟，没有针对芯片的 hack
3. **离线可用**：四个模型全部内置，无任何网络请求
4. **构建全自动化**：push 即构建，8 次 CI 失败全部修复，现在全绿
5. **工具链可复现**：`tools/` 目录可以完整重建模型

### 3.2 不足（诚实列出）

1. **没有真机验证**：APK 没有在真实手机上跑过，只验证了构建产物完整性。绑核策略、内存表现、实际耗时都需要真机数据
2. **性能折算是估算**：Mate60 的 2~2.5x 折算是基于核心数和频率的理论推算，不是实测
3. **只支持 arm64-v8a**：没做 armeabi-v7a / x86
4. **没做 Int8 量化**：fp16 已够用，但量化能再省 2x 时间
5. **鸿蒙兼容层未测试**：卓易通下相册权限代理可能不完整，需要用户反馈后修
6. **UI 功能只有超分**：参考图里的"压缩""相机""关于" tab 没做
7. **无 EXIF 保留**：输出 JPEG 没保留原图元数据
8. **单线程处理队列**：多图是串行处理，没做并行

## 四、未来展望

### 4.1 短期（可立即做）

#### P0：真机验证

**这是当前最大的风险。** 需要用户在真机上测：

- ×2 和 ×4 各跑一张的**实际耗时**
- 四模型**主观画质排序**
- 是否有**崩溃 / 黑图**

拿到数据后才能做针对性优化。

#### P1：性能优化

- **Int8 量化**：模型转 int8，预计再省 2x 时间，代价是可能掉画质（需要重新横评）
- **tile 大小调优**：当前 256px，真机内存数据出来后可调整
- **多图并行**：当前串行，可改成线程池并行处理
- **Y 通道推理**：只对亮度做 SR，色度 bicubic 放大，省 33% 计算

#### P2：功能补全

- 压缩 tab（纯编码参数调节，不需要模型）
- 关于 tab（版本、模型说明、License）
- EXIF 保留
- 保存前预览对比
- 历史记录

### 4.2 中期（需要真机数据支撑）

#### 针对麒麟的优化

当前是"通用方案"，麒麟 9000S 的达芬奇 NPU 有约 6 TOPS int8。如果未来要吃满性能：

- 模型转 MindSpore Lite / NNRT，走 NPU
- 输入可放宽到 8MP（当前 4MP 是纯 CPU 的妥协）
- 但这会绑定华为平台，失去跨平台性

**取舍：跨平台统一（当前方案） vs 单平台极致（NPU 方案）。** 当前选择前者，因为用户要求"同时适配骁龙和麒麟"。

#### 针对骁龙的优化

骁龙的 Hexagon NPU 更成熟，QNN 生态更完整。如果做 NPU 版：

- 骁龙走 QNN（官方文档齐全）
- 麒麟走 MindSpore Lite
- 两套私有栈，工程量翻倍

### 4.3 长期（方向性探索）

#### 模型层面

当前四个模型都是"通用重建"，未来可以：

- **按题材训专用模型**：人像（保肤色）、夜景（去噪）、文档（保笔画）
- **动态模型选择**：根据图片内容（天空占比、噪点水平、文字密度）自动选模型
- **蒸馏更小模型**：把 x4v3 蒸馏到 0.3M 参数，速度再翻 4 倍

#### 算法层面

- **混合方案**：SPAN 做结构重建 + GAN 做纹理增强，按区域融合
- **退化估计**：先估计模糊核和噪声水平，再选最合适的模型和参数
- **分块自适应**：不同 tile 用不同 tile 大小（细节区小 tile，平坦区大 tile）

#### 产品层面

- **实时预览**：取景框实时超分（需要降低推理频率到 2~3 fps）
- **视频超分**：逐帧处理，需要更严格的帧间一致性约束
- **云+端协同**：简单图走端侧，复杂图走云端

### 4.4 一个诚实的提醒

超分模型的效果上限由**输入信息量**决定。降采样到 2MP 再 ×2 输出 8MP，本质是在"补全被丢掉的信息"。模型再强，也补不回 bicubic 已经抹掉的细节。

**正确的期望是**：降采样 + 超分 > 直接 bicubic 放大，且能消除 JPEG 压缩痕迹、模糊、噪点。
**错误的期望是**：12MP 原图能变成 48MP 的"真高清"——物理上不可能。

## 五、方法论沉淀

这次项目留下几条可复用的方法论：

### 5.1 选型三问

任何"著名模型"选型前先问：

1. **权重在哪？**（能下载吗？需要许可吗？）
2. **架构 CPU 友好吗？**（attention 在 CPU 上是灾难）
3. **有数值校验吗？**（转换后要逐像素对比）

### 5.2 测试素材要对齐目标场景

图库照片 ≠ 真实随手拍。测试素材的退化特征（JPEG 压缩、模糊、噪点、构图）必须匹配目标场景，否则结论会失真。

### 5.3 指标不能替代人眼

PSNR/SSIM 测的是"与真值多接近"，人眼测的是"看起来多好"。两者经常给出相反的排名。**最终选型以用户实机观感为准，指标只用于排除硬伤。**

### 5.4 CI 失败要看日志

前 5 次 CI 失败都是因为没看完整日志就猜原因。**完整的错误信息通常直接指向修复方案。**

### 5.5 先验证再优化

先跑通最小版本（能编译、能装、能出图），再做优化。不要一开始就追求完美架构。
